# 系统架构

## 1. 整体架构

小说文本清洗工具采用前后端分离架构：

```
┌─────────────────────────────────────────────────────────┐
│                      前端 (Web Browser)                  │
│  ┌─────────┐  ┌──────────┐  ┌────────┐  ┌─────────────┐  │
│  │文件列表 │  │处理进度  │  │审核界面│  │规则配置     │  │
│  └─────────┘  └──────────┘  └────────┘  └─────────────┘  │
└──────────────────────────┬──────────────────────────────┘
                           │ HTTP REST API
┌──────────────────────────┴──────────────────────────────┐
│                      后端 (Go + Gin)                      │
│  ┌──────────────────────────────────────────────────┐  │
│  │              Handlers (API 处理器)                 │  │
│  │  files.go | process.go | rules.go | versions.go  │  │
│  └──────────────────────────────────────────────────┘  │
│  ┌──────────────────────────────────────────────────┐  │
│  │              Processor (处理流水线)               │  │
│  │  pipeline.go | basic_cleaner.go | vector_detector │  │
│  │  model_repairer.go | processor.go                │  │
│  └──────────────────────────────────────────────────┘  │
│  ┌────────────┐  ┌────────────┐  ┌─────────────────┐  │
│  │  Database  │  │   File     │  │     External    │  │
│  │  (SQLite)  │  │  (MD5/IO)  │  │   (LLM API)     │  │
│  └────────────┘  └────────────┘  └─────────────────┘  │
└────────────────────────────────────────────────────────┘
```

## 2. 模块划分

### 2.1 后端模块

| 模块 | 路径 | 职责 |
|------|------|------|
| config | internal/config | 加载 .env 配置 |
| database | internal/database | SQLite 数据库操作 |
| file | internal/file | MD5 计算、文件名解析、版本管理 |
| processor | internal/processor | 文本处理流水线 |
| review | internal/review/manager | 审核管理 |
| external | internal/external | 外部 API 调用 |
| handlers | web/backend/handlers | HTTP 请求处理 |

### 2.2 处理器模块 (internal/processor)

| 模块 | 说明 |
|------|------|
| pipeline.go | 五步处理流水线控制器，协调各步骤执行 |
| basic_cleaner.go | 第一步：基础文本清洗 |
| vector_detector.go | 第二步：向量索引与检测 |
| model_repairer.go | 第三步：LLM 修复 |
| processor.go | 第四步：审核应用，第五步：最终生成 |
| preprocess/ | 预处理（编码检测、段落分割） |
| postprocess/ | 后处理 |
| rules/ | 规则管理 |
| model/ | NLP 模型封装 |

### 2.3 数据库模块 (internal/database)

| 模块 | 说明 |
|------|------|
| db.go | 数据库初始化与表结构创建 |
| file_repo.go | 文件记录 CRUD |
| version_repo.go | 版本链 CRUD |
| review_repo.go | 审核项 CRUD |
| log_repo.go | 处理日志 CRUD |

## 3. 数据流

### 3.1 文件上传与处理流程

```
用户上传文件
    │
    ▼
解析文件名 → 提取 author, title
    │
    ▼
计算 MD5
    │
    ▼
查询数据库 ──→ 存在？
    │           │
   是          否
    │           │
查询记录    创建新记录
    │
    ▼
显示规则配置界面
    │
    ▼
用户确认规则
    │
    ▼
启动异步处理（goroutine）
    │
    ├── 步骤1: 基础清洗 ──→ 更新进度
    ├── 步骤2: 向量检测 ──→ 更新进度
    ├── 步骤3: LLM修复  ──→ 更新进度
    ├── 步骤4: 生成审核项 ──→ 更新状态
    │
    ▼
进入审核界面
    │
    ▼
用户逐条审核
    │
    ▼
全部审核完成 ──→ 生成最终文件
```

### 3.2 版本链追溯

```
原始文件(MD5-A)
    │
    ▼ 保存清洗后版本
中间版本(MD5-B) ── parent_md5 = MD5-A
    │
    ▼ 保存索引后版本
中间版本(MD5-C) ── parent_md5 = MD5-B
    │
    ▼ 保存LLM修复后版本
中间版本(MD5-D) ── parent_md5 = MD5-C
    │
    ▼ 审核通过
最终文件(MD5-E) ── parent_md5 = MD5-D
```

### 3.3 进度恢复流程

```
用户上传文件 / 点击继续处理
    │
    ▼
查询 files 表获取记录
    │
    ▼
获取 current_step 字段
    │
    ▼
从 current_step 继续执行剩余步骤
```

## 4. 前端架构

单页应用 (SPA)，通过 JavaScript 动态切换显示区域：

| 区域 | ID | 说明 |
|------|-----|------|
| 文件列表 | `#file-list-section` | 显示所有文件卡片 |
| 处理进度 | `#processing-section` | 显示处理进度条和当前操作 |
| 审核界面 | `#review-section` | 显示待审核项列表 |
| 规则配置 | `#rules-section` | 显示规则配置表单 |

### 4.1 状态管理

```javascript
let currentFileMd5 = null;  // 当前选中的文件 MD5
let pollingTimer = null;   // 轮询定时器
```

### 4.2 轮询机制

- 处理开始后，每秒轮询 `/api/files/:md5/status`
- 获取进度、当前步骤、当前操作内容
- 审核阶段时，轮询审核项数量变化
- 处理完成或进入审核时停止轮询

## 5. 关键设计决策

### 5.1 为什么用 MD5 作为文件标识

- 同一文件上传多次，MD5 相同，可识别为同一文件
- 中间版本文件也可通过 MD5 关联到原始文件
- 版本链通过 parent_md5 实现完整追溯

### 5.2 为什么用 SQLite

- 单人使用，无需复杂的事务支持
- 文件存储于本地，SQLite 无需独立部署
- Go 的 modernc.org/sqlite 驱动性能良好

### 5.3 为什么用异步处理

- LLM API 调用耗时长，同步处理会导致 HTTP 超时
- 异步处理允许用户关闭浏览器，后台继续执行
- 通过轮询获取进度，实现准实时的进度展示

### 5.4 为什么按段落处理 LLM 修复

- API 有 token 限制，大段落可能被截断
- 便于逐段落展示进度，缓解用户等待焦虑
- 单段落失败不影响其他段落
