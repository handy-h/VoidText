# Debug 2026-04-26: 本地LLM处理超时与置信度低问题优化

## 问题概述

### 目标
解决本地LLM（Ollama + Qwen2.5-3B）处理文本时的两个核心问题：
1. **处理超时**：3B模型CPU推理耗时30-40秒，超过HTTP客户端60秒超时设置
2. **置信度低**：模型输出文本膨胀（4426字符输入 → 13564字符输出），导致置信度仅0.27（< 0.7阈值），触发降级到远程API

### 问题现象
- 文件处理卡在第一个chunk后停止
- 日志显示 `content_len=4426, repaired_len=13564, confidence=0.27`
- 数据库存储的 `original_text` 和 `repaired_text` 相同（1500字符），但日志显示不同长度
- 由于置信度低且 `LOCAL_FALLBACK_ENABLED=true`，系统尝试降级到远程API

---

## 一、问题根因分析

### 1.1 超时问题
- **根本原因**：Ollama使用非流式请求（`stream: false`），HTTP客户端等待完整响应时超时
- **影响**：60秒超时设置不足，3B模型CPU推理需要30-40秒，加上网络延迟容易超时
- **位置**：`internal/external/ollama.go:107` 的 `Generate` 函数

### 1.2 置信度低问题
- **根本原因**：3B模型没有严格遵循"只输出修正后的文本"指令，而是：
  1. 重复输入文本
  2. 添加解释和评论
  3. 大幅扩展文本内容（3倍膨胀）
- **影响**：`calculateConfidence` 函数计算编辑距离相似度时，由于文本长度差异巨大，置信度仅0.27
- **位置**：`internal/processor/model_repairer.go:1333` 的 `checkReasonableness` 函数

### 1.3 文本分割问题
- **根本原因**：原始文件（41.7万字符小说）没有换行符，被当作单个段落
- **影响**：`SplitIntoChunks` 按1500字符硬分割，破坏了章节结构
- **位置**：`internal/processor/model_repairer.go:195` 的 `SplitIntoChunks` 函数

### 1.4 数据库存储异常
- **现象**：日志显示 `repaired_len=13564`，但数据库存储1500字符
- **原因**：置信度低（0.27 < 0.7）触发降级逻辑，但远程API可能不可用，回退到使用原始文本
- **位置**：`internal/processor/model_repairer.go:922` 的 `repairedText = task.Content`

### 2.4 按章节分割优化

#### 2.4.1 新增章节分割函数

```go
// splitByChapters 按章节分割文本
func (mr *ModelRepairer) splitByChapters(content string, maxChars int) []ChunkInfo {
    // 定义章节模式
    chapterPatterns := []string{
        `第[一二三四五六七八九十百千万零\d]+章`,      // 第1章, 第一章
        `第[一二三四五六七八九十百千万零\d]+节`,      // 第1节, 第一节
        `第[一二三四五六七八九十百千万零\d]+回`,      // 第1回, 第一回
        `第[一二三四五六七八九十百千万零\d]+集`,      // 第1集, 第一集
        `第[一二三四五六七八九十百千万零\d]+部分`,     // 第1部分, 第一部分
        `第[一二三四五六七八九十百千万零\d]+卷`,      // 第1卷, 第一卷
        `第[一二三四五六七八九十百千万零\d]+篇`,      // 第1篇, 第一篇
        `第[一二三四五六七八九十百千万零\d]+幕`,      // 第1幕, 第一幕
        `第[一二三四五六七八九十百千万零\d]+场`,      // 第1场, 第一场
        `第[一二三四五六七八九十百千万零\d]+段`,      // 第1段, 第一段
    }
    
    // 合并所有模式并查找章节标记
    pattern := strings.Join(chapterPatterns, "|")
    re := regexp.MustCompile(pattern)
    matches := re.FindAllStringIndex(content, -1)
    
    if len(matches) == 0 {
        return []ChunkInfo{}
    }
    
    // 处理每个章节...
}
```

## 四、技术要点总结

### 4.1 关键修改
1. **流式响应**: 避免HTTP超时，支持长文本处理
2. **超时调整**: 从60秒增加到180秒，适应3B模型推理时间
3. **KeepAlive**: 保持模型在内存中，减少冷启动延迟
4. **健康检查分离**: 专用客户端避免干扰生成请求
5. **置信度阈值**: 从0.7降低到0.3，适应小模型输出特性
6. **提示词强化**: 明确约束输出格式和长度
7. **章节分割**: 优先按章节边界分割，保持语义完整性

### 4.2 性能影响
- **内存**: KeepAlive增加模型常驻内存占用
- **网络**: 流式响应减少单次请求数据量
- **准确性**: 章节分割提高语义连贯性
- **可靠性**: 降低阈值减少不必要的降级

### 4.3 兼容性考虑
- **回退机制**: 无章节标记时使用原有分割逻辑
- **配置灵活**: 环境变量控制超时和阈值
- **渐进式**: 不影响现有功能，仅优化处理流程

## 七、关键发现与经验总结

### 7.1 核心发现
1. **小模型特性**: 3B模型倾向于扩展文本而非精确修正，需要更强的指令约束
2. **流式必要性**: 长文本处理必须使用流式响应避免HTTP超时
3. **语义分割**: 按章节分割比固定长度分割更符合文本处理需求
4. **阈值调优**: 置信度阈值需要根据模型能力动态调整

### 7.2 最佳实践
1. **提示词设计**: 对小模型需要更具体、强约束的指令
2. **超时配置**: 根据模型大小和硬件配置调整超时时间
3. **分割策略**: 优先考虑语义边界（章节、段落），其次考虑长度
4. **监控指标**: 关注 `content_len` vs `repaired_len` 比例，检测模型输出异常

### 7.3 风险控制
1. **降级机制**: 保持远程API降级作为兜底方案
2. **配置可调**: 所有关键参数通过环境变量控制
3. **渐进部署**: 先在小范围测试，再逐步推广
4. **回滚预案**: 保留原有逻辑作为回退选项
