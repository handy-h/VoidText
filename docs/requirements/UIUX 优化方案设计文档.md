(VoidText) UI/UX 优化方案设计文档
一、 核心设计理念
从“工具”向“工作站”转变：不仅是运行脚本，而是提供一个高效、沉浸的处理环境。

工作流闭环：减少不必要的操作跳转，保持用户心流。

聚焦式审核：解决长篇大论带来的视觉疲劳，通过“批量聚合”提升审核效率。

二、 交互流程重构方案
1. 初始化与上传 
现状：列表为空时视觉中心缺失，上传按钮位置偏远。

优化建议：将原本的“暂无文件”列表区域改造为一个巨大的“拖拽上传区”。中心放置显眼的上传图标，文字提示：“点击选择或拖拽小说文件（.txt / .docx）至此开始处理”。

自动化：文件选择/拖拽完成后，系统应直接进入“规则配置”步骤，减少用户点击“配置”按钮的手动操作。

2. 规则配置与启动 (优化 SceenPrint_20260430_204127.jpg)
现状：保存与开始处理是分离的思维动作。

优化建议：将“保存”按钮强化为“保存并开始处理”。同时，在配置界面提供常用的预设模板，如“基础清洗模式”或“深度修复模式”，降低新用户的上手成本。

3. 处理进度监控 (优化 SceenPrint_20260430_210016.jpg)
现状：必须点进详情页才能看到进度。

优化建议：在文件列表卡片上直接外显进度条。例如在卡片底部显示一条极细的进度线，并标注“LLM修复中... 45%”。

智能跳转：增加一个开关选项：“处理完成后自动进入审核页面”。

三、 核心重构：人工审核页面 
这是本方案改进的重中之重，旨在解决你提到的“分段不清晰”和“无法批量修改”的痛点。

1. 布局重组：双栏导航架构
建议左侧为“修改项分类导航”，右侧为“沉浸式对比编辑区”。

2. 左侧：修改项聚合面板 (解决批量修改需求)
不按字数强行分段，而是按逻辑特征聚合：

全部待审核：显示总的修改点位数量。

高频词汇类：将相同的修改项归类。例如：显示“的地得纠正 (25处)”、“做/坐/座纠正 (12处)”。每个条目旁提供 [全部采纳] 和 [全部忽略] 按钮。

语义逻辑类：展示 LLM 判定为语病或逻辑不通的重写建议。

清洗类：展示正则匹配到的广告或无用符号清理。

3. 右侧：VS Code 风格的内联对比视图 (解决看不清需求)
放弃左右大段对比，改用垂直内联（Line-by-line Diff）模式：

卡片化呈现：每一个修改点位是一个独立的审核卡片。

上下文智能折叠：默认仅显示修改行及其前后各 1 行内容。点击卡片边缘可展开全文上下文。

视觉对比标准：

原文行：浅红色背景。对被删除/替换的词汇使用深红色高亮并加删除线。

建议行：浅绿色背景。对修改后的词汇使用深绿色高亮并加粗。

单点操作：每个卡片右侧悬浮 [✓ 采纳]、[✗ 拒绝]、[✎ 手动微调] 三个图标。

4. 批量操作逻辑
当用户在左侧选中某个具体词汇（如“做坐纠正”）时，右侧主视图连续展示该词汇在全文中出现的所有修改位置。用户可以快速滑动滚轮查看上下文，然后点击顶部的“本页全部采纳”完成操作。

四、 视觉与反馈优化建议
状态标签化：在列表页中使用不同颜色的标签区分状态：待配置（灰色）、处理中（蓝色）、待审核（橙色）、已完成（绿色）。

Toast 提示：上传成功或处理完成后，使用自动消失的黑色半透明提示框，避免使用需要手动关闭的大弹窗。

快捷键支持：审核页面应支持键盘流操作。↑/↓ 键切换当前选中的修改卡片，Enter 键采纳，Esc 键拒绝。

配色方案：延续当前的深暗色调（Deep Charcoal），这有助于用户长时间盯着屏幕寻找错别字时减少眼部疲劳。

设计目标总结：让原本枯燥的校对过程变得像“刷信息流”一样丝滑，通过批量聚合逻辑彻底消灭重复劳动。
