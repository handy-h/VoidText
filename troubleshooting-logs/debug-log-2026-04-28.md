# Debug 2026-04-28: 任务进度卡在40%问题分析

## 问题概述

### 目标
分析为什么本地Ollama模型完成文本处理后，任务进度仍然停留在40%不前进。

### 问题现象
- Ollama后台显示处理成功（`POST /api/generate` 耗时约1分42秒）
- Gin日志显示状态查询正常（`GET /api/files/:md5/status` 返回200）
- 但任务进度始终显示40%，未推进到下一阶段（应为60%，进入人工审核阶段）

---

## 一、问题根因分析

### 1.1 进度计算机制

VoidText采用5步流水线，每步贡献20%总进度：

| 步骤 | 索引 | 基础进度 | 进度范围 |
|------|------|----------|----------|
| 基础清洗 (cleaning) | 0 | 0% | 0-20% |
| 向量检测 (indexing) | 1 | 20% | 20-40% |
| **LLM修复 (llm_fix)** | 2 | **40%** | **40-60%** |
| 人工审核 (review) | 3 | 60% | 60-80% |
| 生成文件 (finalizing) | 4 | 80% | 80-100% |

**进度计算公式**（`internal/processor/pipeline.go:96-101`）：
```go
func CalculateProgress(step string, stepProgress int) int {
    stepIdx := GetStepIndex(step)
    baseProgress := stepIdx * 20
    stepContribution := stepProgress * 20 / 100
    return baseProgress + stepContribution
}
```

当LLM修复步骤开始时，`CalculateProgress(StepLlmFix, 0)` = `2 * 20 + 0` = **40%**。

### 1.2 关键代码流程

**步骤启动**（`pipeline.go:307`）：
```go
StartProcessingStep(fileMd5, StepLlmFix)  // 设置 progress=40%, status="processing"
```

**模型处理**（`pipeline.go:323`）：
```go
repairResult := repairer.RepairTextWithFileMd5(...)  // Ollama处理chunks
```

**进度追踪器清理**（`pipeline.go:340`）：
```go
GlobalProgressTracker.FinishTracking(fileMd5)  // 清除内存中的进度追踪器
```

**步骤完成**（`pipeline.go:387`）：
```go
CompleteProcessingStep(fileMd5, StepLlmFix, ...)  // 更新数据库: progress=60%, current_step="review"
```

### 1.3 竞态条件分析

**问题核心**：在第340行（`FinishTracking`）和第387行（`CompleteProcessingStep`）之间存在时间窗口。

如果在此窗口内发生：
- goroutine被抢占或崩溃
- 数据库更新失败
- 处理过程中出现未捕获的错误

则文件将永远停留在40%，因为：
- `GlobalProgressTracker`已被清除（内存中无进度信息）
- 数据库仍显示：`progress=40%, current_step='llm_fix', status='processing'`
- `CompleteProcessingStep`从未被调用或未成功执行

### 1.4 前端状态查询

**查询逻辑**（`web/backend/handlers/process.go:127-132`）：
```go
if record.CurrentStep == "llm_fix" && record.Status == "processing" {
    if progressInfo, exists := processor.GlobalProgressTracker.GetProgress(fileMd5); exists {
        response["chunkProgress"] = progressInfo
    }
}
```

**问题表现**：
- `GlobalProgressTracker.GetProgress`返回`exists=false`（已被FinishTracking清除）
- `record.Progress`仍从数据库读取40%
- 前端显示进度卡在40%不动

### 1.5 潜在崩溃点

**第387行`repairResult.Stats`访问**：
```go
totalChunks := repairResult.Stats["total_chunks"]  // 可能panic如果Stats为nil
```

可能发生的情况：
- `EnableModelRepair=false`时，`RepairTextWithFileMd5`提前返回
- `chunks`为空时，提前返回
- 上述两种情况下`Stats`可能未初始化（nil map）

## 四、技术要点总结

### 4.1 进度机制理解
1. **两步式进度**：
   - 全局进度（0-100%）由步骤索引×20 + 步骤内进度×20/100计算
   - 内存进度追踪器负责跟踪块级处理进度

2. **内存→数据库同步**：
   - 内存追踪器先清理（第340行）
   - 数据库后更新（第387行）
   - **存在时间窗口**

### 4.2 正常流程
```
LLM修复开始 → 进度=40%
    ↓
Ollama处理chunks（块级进度更新到内存追踪器）
    ↓
处理完成 → FinishTracking（清除内存追踪器）
    ↓
CompleteProcessingStep（更新数据库: progress=60%, step=review）
    ↓
进入人工审核阶段
```

### 4.3 异常流程（卡在40%）
```
LLM修复开始 → 进度=40%
    ↓
Ollama处理完成（内存追踪器有进度）
    ↓
FinishTracking（内存追踪器已清除）
    ↓
??? 错误/崩溃/中断 ???
    ↓
CompleteProcessingStep 未执行
    ↓
数据库仍显示: progress=40%, step=llm_fix, status=processing
```

## 七、2026-04-28 修复记录

### 7.1 修复内容

对 `internal/processor/pipeline.go` 中 `processLlmFixStep` 函数（第 272-431 行）实施了 3 项修复：

#### 修复 1：添加 `defer` panic 恢复机制（第 311-329 行）

```go
var repairResult ModelRepairResult
defer func() {
    if r := recover(); r != nil {
        logging.Error("llm_fix_panic_recovered", nil, map[string]interface{}{
            "file_md5": fileMd5,
            "panic":    fmt.Sprintf("%v", r),
        })
        CompleteProcessingStep(fileMd5, StepLlmFix, map[string]interface{}{
            "error":  fmt.Sprintf("panic: %v", r),
            "status": "recovered",
        })
    }
}()
```

如果函数体内任意位置发生 panic（如 nil map 访问、文件 I/O 崩溃等），defer 会捕获并强制调用 `CompleteProcessingStep`，确保数据库进度不会永远卡在 40%。

#### 修复 2：`FinishTracking` 移到 `CompleteProcessingStep` 之后（第 419-420 行）

```go
// 先更新数据库
CompleteProcessingStep(fileMd5, StepLlmFix, ...)
// 数据库成功后才清理内存中的进度追踪器
GlobalProgressTracker.FinishTracking(fileMd5)
```

**消除竞态窗口**：
- **修复前**：`FinishTracking` → [竞态窗口] → `CompleteProcessingStep`
- **修复后**：`CompleteProcessingStep` → `FinishTracking`

即使 `CompleteProcessingStep` 执行后仍有问题，`GetFileStatus` 查询数据库时 `currentStep` 已经是 `"review"`，前端无需依赖内存进度追踪器来更新进度。

#### 修复 3：`repairResult.Stats` nil 安全检查（第 347-351 行）

```go
stats := repairResult.Stats
if stats == nil {
    stats = make(map[string]int)
}
```

防御性 nil map 检查，防止所有后续的 `stats["xxx"]` 读取操作因 map 未初始化而 panic。
