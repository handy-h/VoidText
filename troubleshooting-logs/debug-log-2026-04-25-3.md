# Debug 2026-04-25 (续2) - mock_ollama 验证与三个 Bug 修复

## 问题概述

### 目标

使用 `mock_ollama.py` 模拟本地 Ollama，替代真实 LLM 返回置信度为 1 的数据，验证文本清洗流程能继续下去。

### 遇到的问题

在验证过程中，依次发现并修复了三个 Bug：

1. **健康检查竞态条件**：`processChunk` 在健康检查完成前执行，`ShouldUseLocalModel()` 返回 false，本地模型未被使用
2. **WaitGroup 缺少 Done**：`processTask` 没有调用 `wg.Done()`，导致 `ProcessChunks` 永久阻塞
3. **CheckReviewComplete 逻辑错误**：没有审核项时返回 false，无法进入 finalizing 步骤

---

## 一、mock_ollama.py 改造

### 原始问题

原始 `mock_ollama.py` 的 `/api/generate` 端点直接将整个 `prompt` 作为 `response` 返回：

```python
"response": prompt,  # 返回整个 prompt
```

但 VoidText 的 `CorrectText()` 构造的 prompt 格式为：

```go
userPrompt := "请纠正以下文本中的错别字和语法错误：\n" + text + "\n\n修正后的文本："
```

所以 `response` 返回的是带前缀和后缀的完整 prompt，而不是原始文本。这导致 `calculateConfidence(original, repaired)` 中 `original != repaired`，置信度远低于阈值 0.7。

### 修改方案

从 prompt 中剥离已知的 `PROMPT_PREFIX` 和 `PROMPT_SUFFIX`，提取原始文本并原样返回：

```python
PROMPT_PREFIX = "请纠正以下文本中的错别字和语法错误：\n"
PROMPT_SUFFIX = "\n\n修正后的文本："

def extract_original_text(prompt: str) -> str:
    if prompt.startswith(PROMPT_PREFIX) and prompt.endswith(PROMPT_SUFFIX):
        original = prompt[len(PROMPT_PREFIX) : -len(PROMPT_SUFFIX)]
        return original
    return prompt  # fallback
```

返回时：

```python
"response": original_text,  # 返回原始文本，使 original == repaired
```

### 效果

- `calculateConfidence(original, repaired)` 判定 `original == repaired`，返回 `MaxConfidence = 1.0`
- 置信度 1.0 >= 阈值 0.7，本地模型处理成功
- 处理耗时从 100-150 秒（CPU 推理）降至 5ms

### 其他改进

- `/api/tags` 返回符合 Ollama 真实格式的响应（含 `models` 数组），确保 `HealthCheck()` 通过
- 添加 `/` 根端点，方便验证 mock 服务是否运行
- 添加 `--port` 和 `--host` 命令行参数

## 二、Bug 1：健康检查竞态条件

### 现象

- 启动 VoidText 后触发文件处理，进度卡在 `llm_fix` 步骤 40%
- 数据库中 chunk 0 的 `source` 为 `remote`（不是 `local`）
- `local_success: 0, local_failure: 0`，本地模型完全没被调用
- 远程 MiniMax API 返回 400/500 错误

### 排查过程

#### 1. 检查 stderr 日志时间线

```
15:10:09.352 health_check_started     -- 健康检查在 NewWorkerPool 中启动
15:10:09.352 llm_fix_start            -- llm_fix 几乎同时开始
15:10:09.969 api_request_completed    -- 直接调用了远程 MiniMax API！
15:10:52.581 ollama_health_check      -- 健康检查在 30 秒后才第一次执行
```

#### 2. 分析根因

`Start()` 方法中 `go hcm.runHealthChecks()` 启动了一个 goroutine：

```go
func (hcm *HealthCheckManager) Start() error {
    hcm.running = true
    go hcm.runHealthChecks()  // goroutine 调度不保证立即执行
    return nil
}
```

虽然 `runHealthChecks()` 的第一行是 `hcm.performHealthChecks()`，但 Go 的 goroutine 调度不保证立即执行。在 `Start()` 返回后、goroutine 实际执行前，`ProcessChunks` 已经提交任务到 `taskQueue`，worker 取出任务并调用 `processChunk`。

此时 `ShouldUseLocalModel()` 检查 `status.Healthy && status.Enabled`，而 `Healthy` 初始值为 `false`（在 `RegisterService` 中设置），所以返回 `false`，直接走了远程 API 路径。

#### 3. 验证

从状态文件的时间戳确认：

```
Start:          2026-04-25T22:03:27.864732708+08:00
处理第0个块:    2026-04-25T22:03:27.866120308+08:00
```

从开始处理到处理第 0 个块只用了 **1ms**，健康检查 goroutine 根本来不及执行。

### 修复

**文件**：`internal/processor/health_check.go`

**修改前**：

```go
func (hcm *HealthCheckManager) Start() error {
    hcm.running = true
    go hcm.runHealthChecks()
    return nil
}

func (hcm *HealthCheckManager) runHealthChecks() {
    hcm.performHealthChecks()  // 在 goroutine 中执行，有调度延迟
    ticker := time.NewTicker(hcm.checkInterval)
    defer ticker.Stop()
    for {
        select {
        case <-ticker.C:
            hcm.performHealthChecks()
        case <-hcm.stopChan:
            return
        }
    }
}
```

**修改后**：

```go
func (hcm *HealthCheckManager) Start() error {
    hcm.running = true

    // 同步执行第一次健康检查，确保初始状态正确
    // 避免goroutine调度延迟导致processChunk在健康检查完成前运行
    hcm.performHealthChecks()

    // 启动后台定期检查
    go hcm.runHealthChecksLoop()
    return nil
}

// runHealthChecksLoop 定期执行健康检查的循环
func (hcm *HealthCheckManager) runHealthChecksLoop() {
    ticker := time.NewTicker(hcm.checkInterval)
    defer ticker.Stop()
    for {
        select {
        case <-ticker.C:
            hcm.performHealthChecks()
        case <-hcm.stopChan:
            return
        }
    }
}
```

**关键改动**：将第一次 `performHealthChecks()` 从 goroutine 中移到 `Start()` 中同步执行，确保 `Start()` 返回时健康状态已经正确设置。

### 修复后日志验证

```
15:10:09.352 ollama_health_check  healthy=true  -- 同步执行，立即完成
15:10:09.352 service_healthy      service=ollama
15:10:09.352 health_check_started
15:10:09.355 chunk_processing_strategy  useLocal=true  -- 本地模型被使用！
15:10:09.355 local_model_processing_start
15:10:09.358 local_model_processing_success  confidence=1
```

## 三、Bug 2：WaitGroup 缺少 Done 调用

### 现象

- 修复 Bug 1 后，本地模型被成功调用（日志显示 `local_model_processing_success, confidence=1`）
- `chunk_repair_cache` 中有记录（`source=local, confidence=1.0`）
- 但进度仍然卡在 `llm_fix` 40%，流程无法推进
- 状态文件显示 `processed=0`，chunk 0 状态为 `processing`（不是 `completed`）

### 排查过程

#### 1. 分析数据不一致

- `chunk_repair_cache` 有记录 → `SaveChunkRepair` 成功执行
- 但状态文件 `processed=0` → `ProcessChunks` 没有完成结果收集
- `local_success=0` → 统计计数器没有更新

这说明 `processChunk` 成功执行并保存了缓存，但 `ProcessChunks` 在收集结果时阻塞了。

#### 2. 检查 ProcessChunks 的结果收集逻辑

```go
func (wp *WorkerPool) ProcessChunks(...) []ChunkResult {
    wp.wg.Add(len(chunksToProcess))   // 第1106行：Add(1)

    // 提交任务
    wp.taskQueue <- task

    // 收集结果
    for i := 0; i < len(chunksToProcess); i++ {
        result := <-wp.results         // 第1122行：从 results channel 读取
        results = append(results, result)
    }

    wp.wg.Wait()                       // 第1126行：等待 WaitGroup
    ...
}
```

#### 3. 检查 processTask

```go
func (wp *WorkerPool) processTask(task ChunkTask) {
    result := wp.processChunk(task)
    wp.results <- result
    // 没有 wg.Done()！
}
```

#### 4. 根因确认

`wg.Add(1)` 在 `ProcessChunks` 中调用，但 `processTask` 中没有对应的 `wg.Done()`。`wg.Wait()` 会永远阻塞，导致 `ProcessChunks` 无法完成。

虽然 `results` channel 能收到结果（`processTask` 发送了），但 `wg.Wait()` 在结果收集之后，永远等不到 `Done()`，所以整个函数阻塞。

### 修复

**文件**：`internal/processor/model_repairer.go`

**修改前**：

```go
func (wp *WorkerPool) processTask(task ChunkTask) {
    result := wp.processChunk(task)
    wp.results <- result
}
```

**修改后**：

```go
func (wp *WorkerPool) processTask(task ChunkTask) {
    defer wp.wg.Done()

    result := wp.processChunk(task)
    wp.results <- result
}
```

### 修复后效果

- llm_fix 步骤成功完成，进度从 40% 推进到 80%
- 处理日志显示 `llm_fix complete: 修复完成：1个块，0处修改`
- 状态文件显示 `processed=1/1, local_success=1`

## 四、Bug 3：CheckReviewComplete 逻辑错误

### 现象

- llm_fix 步骤成功完成后，流程推进到 finalizing（80%）
- 但调用 `/api/files/{md5}/finalize` 接口返回 `"还有未审核的项目"`
- 实际上 `review_items` 表为空（没有审核项）

### 排查过程

#### 1. 检查 FinalizeFile 接口

```go
func FinalizeFile(c *gin.Context) {
    complete, err := processor.CheckReviewComplete(fileMd5)
    if !complete {
        c.JSON(400, gin.H{"success": false, "message": "还有未审核的项目"})
        return
    }
    ...
}
```

#### 2. 检查 CheckReviewComplete

```go
func CheckReviewComplete(fileMd5 string) (bool, error) {
    total, resolved, err := database.GetReviewProgress(fileMd5)
    return total > 0 && total == resolved, nil
}
```

#### 3. 根因

当 `total == 0`（没有审核项）时，`total > 0` 为 false，整个表达式为 false。

但语义上，如果没有审核项，应该认为审核已完成（无需审核 = 审核通过）。

### 修复

**文件**：`internal/processor/pipeline.go`

**修改前**：

```go
return total > 0 && total == resolved, nil
```

**修改后**：

```go
// 没有审核项时视为审核完成，有审核项时需全部解决
return total == 0 || total == resolved, nil
```

### 修复后效果

- 调用 `/api/files/{md5}/finalize` 成功
- 最终文件正确生成
- 文件状态更新为 `completed, progress=100%`

## 七、Bug 影响分析

| Bug | 影响范围 | 严重程度 | 触发条件 |
|-----|----------|----------|----------|
| 健康检查竞态 | 所有使用本地模型的文件处理 | 严重 | 每次启动 VoidText 后首次处理文件时必现 |
| WaitGroup 缺少 Done | 所有 llm_fix 步骤 | 严重 | 每次处理文件时必现（之前可能被其他路径掩盖） |
| CheckReviewComplete 逻辑 | 无审核项的文件 | 中等 | LLM 修复后没有产生变更时触发 |

### 为什么之前没有暴露

1. **健康检查竞态**：之前使用真实 Ollama 时，CPU 推理极慢（100-150秒/chunk），健康检查在处理开始前早已完成。使用 mock_ollama 后处理速度极快（5ms），竞态窗口才暴露。

2. **WaitGroup 缺少 Done**：之前流程卡在健康检查竞态（直接走远程 API），`ProcessChunks` 的 `wg.Wait()` 阻塞被其他错误掩盖。修复竞态后本地模型被使用，`wg.Wait()` 的阻塞才显现。

3. **CheckReviewComplete 逻辑**：之前流程从未走到 finalizing 步骤，此 bug 从未被触发。

## 八、备注

1. mock_ollama 的 `extract_original_text()` 依赖 `CorrectText()` 的 prompt 格式。如果 `CorrectText()` 的 prompt 格式变化，mock 需要同步更新。
2. 修复后的二进制文件为 `voidtext_new`，需要替换原来的 `voidtext`。
3. mock_ollama 仅用于开发测试，不应在生产环境使用。
4. 当前系统无 GPU，真实 Ollama 使用 CPU 推理，7B 模型处理每个 chunk 需 100-150 秒。mock_ollama 将此降至 5ms，极大提升了开发迭代效率。
