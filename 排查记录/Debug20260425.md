# 调试记录 2026-04-25

## 问题概述

### 核心问题：文本编码错误导致置信度计算异常

**现象**：
- 数据库中 `original_text` 和 `repaired_text` 字节完全相同
- 但置信度极低：0.0187、0.0617、0.155 等
- `calculateConfidence()` 在 `original == repaired` 时应返回 1.0，但实际返回低值

**根本原因**：
- 上传的文本文件是 GBK 编码，但在处理时被错误地读取为 UTF-8
- 每个 GBK 双字节字符被转换为 UTF-8 替换字符（U+FFFD, `�`，字节序列 EF BF BD）
- 替换字符是有效的 UTF-8，所以 `utf8.ValidString()` 返回 true，编码检测被跳过
- Levenshtein 距离计算将替换字符视为不同字符，导致相似度极低

## 排查过程

### 1. 验证置信度计算逻辑

文件：`internal/processor/model_repairer.go:1194-1217`

```go
func (wp *WorkerPool) calculateConfidence(original, repaired string) float64 {
    if original == repaired {
        return DefaultConfidenceConfig.MaxConfidence  // 应该返回 1.0
    }
    // ...
}
```

**结论**：逻辑正确，问题不在算法本身。

### 2. 检查数据库中的文本

```sql
SELECT original_text, repaired_text, confidence FROM chunk_repair_cache LIMIT 3;
```

**发现**：
- 原始文本和修复文本都包含大量替换字符 `�`
- SQL 字符串比较返回 true（字节完全相同）
- 但置信度很低（0.569, 0.012, 0.155）

### 3. 检查源文件编码

```bash
file -i data/uploads/6f32ed28546fb02ec39873abace37cce_于冒泡~恶搞暗黑破坏神.txt
# 输出: text/plain; charset=unknown-8bit  (原始文件，GBK编码)

file -i data/uploads/6f32ed28546fb02ec39873abace37cce_cleaning.txt
# 输出: text/plain; charset=utf-8  (清洗文件，包含替换字符)
```

**关键发现**：
- 原始文件是 GBK 编码（869,672 字节）
- 清洗文件是 UTF-8 编码但包含 539,965 个替换字符（1,906,932 字节）
- 文件大小从 869KB 膨胀到 1.9MB，因为每个 GBK 双字节字符变成了 3 字节的 UTF-8 替换字符

### 4. 验证 GBK 解码

用 GBK 解码器解码原始文件字节：
```
前100字符: "《恶搞暗黑破坏神》\r\n于冒泡\r\n\r\n序章\r\n谨以此长篇爆笑同人小说献给所有忠..."
替换字符数量: 0
```

**结论**：原始文件是正确的 GBK 编码中文文本，解码后无替换字符。

### 5. 定位编码转换缺失点

文件：`internal/processor/pipeline.go:114`

```go
content, err := os.ReadFile(record.FilePath)
// 直接将字节转换为字符串，没有编码检测
```

文件：`internal/processor/preprocess/preprocess.go:52-63`

```go
func normalizeEncoding(result PreprocessResult) PreprocessResult {
    if utf8.ValidString(result.Content) {
        return result  // 替换字符是有效的UTF-8，直接跳过！
    }
    // ...
}
```

**问题**：`utf8.ValidString()` 对包含替换字符的字符串返回 true，导致编码修复被跳过。

## 已完成的修复

### 修复1：在 pipeline.go 中添加字节级编码检测

文件：`internal/processor/pipeline.go`

**修改前**：
```go
content, err := os.ReadFile(record.FilePath)
// 直接使用 string(content)
```

**修改后**：
```go
contentBytes, err := os.ReadFile(record.FilePath)
preprocessResult, err := preprocess.PreprocessBytes(contentBytes)
content := preprocessResult.Content
```

### 修复2：添加 PreprocessBytes 和 detectAndConvertToUTF8 函数

文件：`internal/processor/preprocess/preprocess.go`

新增函数：
- `PreprocessBytes(data []byte)` - 在字节转字符串前检测编码
- `detectAndConvertToUTF8(data []byte)` - 自动检测 GBK/GB18030 并转换

核心逻辑：
1. 检查字节是否包含 UTF-8 替换字符序列（EF BF BD）
2. 如果包含，尝试用 GBK/GB18030 解码原始字节
3. 如果解码后无替换字符，使用解码结果
4. 如果所有解码都失败，尝试修复混合编码

### 修复3：改进 normalizeEncoding 函数

**修改前**：只检查 `utf8.ValidString()`

**修改后**：
1. 先检查是否包含替换字符 `�`
2. 如果包含，尝试修复
3. 再检查 `utf8.ValidString()`

### 修复4：添加乱码兜底处理

文件：`internal/processor/preprocess/preprocess.go`

新增函数：
- `cleanupGarbledText(result)` - 清理无法修复的乱码
- `isLikelyGarbled(text)` - 判断文本是否是乱码

处理逻辑：
1. **连续替换字符**：3个及以上连续的 `�` 被识别为乱码
2. **常见乱码模式**：`锟斤拷`、`烫烫烫`、`屯屯屯` 等经典乱码
3. **无法识别的字符序列**：非中文、非标点、非ASCII的连续字符

替换规则：
- 删除乱码内容
- 插入提示文字：`[因无法修复的乱码删除了N个字符]`
- 记录变更到 `result.Changes`

### 修复5：清理损坏的缓存数据

- 清除了 `chunk_repair_cache` 表中的 3 条损坏记录
- 重置文件状态为 `pending`，步骤为 `cleaning`
- 将文件路径重置为原始 GBK 文件
