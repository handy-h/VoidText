# Debug 2026-04-30: "保存并开始处理"按钮无反应

## 问题概述

文件上传后，点击文件卡片上的"配置并处理"→ 进入规则配置表单 → 点击"保存并开始处理"按钮 **无任何反应**（无网络请求、无错误提示、页面不跳转）。

---

## 一、问题根因

### 1.1 双重 `currentFileMd5` 变量冲突

代码库中存在**两个并行的 JavaScript 架构**：遗留的 `main.js` 单体和新的 `modules/*.js` 模块化架构。两者都声明了各自的 `currentFileMd5` 变量：

| 变量 | 位置 | 作用域 |
|------|------|--------|
| `currentFileMd5` | `main.js:1` | **全局** `window.currentFileMd5` |
| `currentFileMd5` | `rules-config.js:4` | **模块私有**（IIFE 内部） |

**用户操作流程追踪：**

```
步骤1: 用户点击"配置并处理"
  → DomUtils.configureRules(md5)
  → app.js:33 映射到 RulesConfigModule.configureRules   ✅
  → rules-config.js:28 执行
    → 设置模块私有 currentFileMd5 = md5                 ✅
    → 未设置全局 currentFileMd5                         ❌

步骤2: 用户点击"保存并开始处理"
  → HTML onclick="saveRulesAndProcess()"
  → 调用 main.js:1005 全局函数 saveRulesAndProcess()    ⚠️
    → if (!currentFileMd5) return;  // 读取全局变量
    → 全局 currentFileMd5 === null                       ❌ 提前返回！
```

### 1.2 HTML onclick 指向了错误函数

`index.html:141` 使用 `onclick="saveRulesAndProcess()"`，该调用解析到 `main.js` 中的全局函数。但"配置并处理"按钮的回调（`DomUtils.configureRules`）已在 `app.js:33` 中被覆盖为 `RulesConfigModule.configureRules`——因此**配置阶段走模块系统，保存阶段走遗留系统**，两个系统使用不同的 `currentFileMd5`。

### 1.3 轮询阶段的级联故障

即使 onclick 修复了，`RulesConfigModule.startProcessing()` 调用的 `ProcessingModule.startPolling()` 也需要 `ProcessingModule` 自身的 `currentFileMd5` 被设置，否则轮询静默失败（进度永远不更新）。

---

## 二、修复方案

### 修复1：HTML onclick 指向模块函数

**文件**: `web/frontend/index.html:141`

```diff
- <button class="btn-primary" onclick="saveRulesAndProcess()">
+ <button class="btn-primary" onclick="RulesConfigModule.saveRulesAndProcess()">
```

确保"保存并开始处理"按钮调用模块版的 `saveRulesAndProcess`，与模块版的 `configureRules` 使用同一个 `currentFileMd5`。

### 修复2：配置规则时同步设置全局变量

**文件**: `web/frontend/static/js/modules/rules-config.js:29-30`

```diff
  function configureRules(md5) {
    currentFileMd5 = md5;
+   window.currentFileMd5 = md5;  // 同步设置全局变量（防御性兼容）
```

即使其他遗留代码路径依赖全局 `currentFileMd5`，也能正常工作。

### 修复3：启动处理时同步 ProcessingModule 的 currentFileMd5

**文件**: `web/frontend/static/js/modules/rules-config.js:136-138`

```diff
          FileManager.showSection('processing');
+         ProcessingModule.setCurrentFileMd5(currentFileMd5);
          ProcessingModule.startPolling();
```

`ProcessingModule.startPolling()` 内部 `updateProgress()` 依赖其自身的 `currentFileMd5` 发起 `/status` 轮询。未设置时轮询直接 `return`，进度不更新。

## 四、波及影响分析

### 4.1 各入口路径分析

| 入口 | 进入方式 | configureRules 调用方 | 设置哪个 currentFileMd5 | 修复前是否受影响 |
|------|----------|----------------------|------------------------|:---:|
| 上传后"配置规则并处理" | 上传结果UI按钮 | `DomUtils.configureRules` → `RulesConfigModule.configureRules` | 模块私有 | **❌ 是** |
| 文件卡片"配置并处理" | 文件列表卡片按钮 | 同上 | 模块私有 | **❌ 是** |
| 文件卡片"重新处理" | 文件列表卡片按钮 | `FileManager.reprocessFile` → **全局** `configureRules`（main.js:354） | 全局 `window.currentFileMd5` | **❌ 是**（修复1后新增问题） |
| 文件卡片"从失败处恢复" | 文件列表卡片按钮 | `FileManager.resumeFile` → 跳过配置，直接启动 | 不涉及配置环节 | 不受影响 |

### 4.2 "重新处理"路径的额外问题

`FileManager.reprocessFile`（file-manager.js:176）调用的是**无命名空间限定的** `configureRules(md5)`。由于 `FileManager` IIFE 内部未定义 `configureRules`，作用域链查找到**全局** `configureRules`（main.js:354）。

这意味着"重新处理"流程中：
1. `FileManager.reprocessFile` → 全局 `configureRules` → 设置 `window.currentFileMd5`
2. HTML onclick → `RulesConfigModule.saveRulesAndProcess()`（被修复1修改）
3. 模块函数读取的是**模块私有** `currentFileMd5` → 从未被设置 → **提前返回** ❌

### 修复4：防御性 fallback

在 `saveRulesAndProcess` 和 `startProcessing` 中添加 `window.currentFileMd5` fallback：

```javascript
function saveRulesAndProcess() {
    if (!currentFileMd5) currentFileMd5 = window.currentFileMd5 || null;
    if (!currentFileMd5) return;
    ...
}

function startProcessing() {
    if (!currentFileMd5) currentFileMd5 = window.currentFileMd5 || null;
    if (!currentFileMd5) return;
    ...
}
```

这样无论从哪个入口进入，只要全局 `window.currentFileMd5` 被设置了，模块函数就能正常工作。

## 七、架构反思

### 7.1 main.js 与 modules/*.js 的双轨并存

这是目前前端最大的技术债。两个架构各自声明全局/私有变量，通过 `app.js` 中的 `setupDomUtilsCallbacks()` 做"路由"但非常脆弱：

| 方面 | main.js（遗留） | modules/*.js（新） |
|------|----------------|-------------------|
| `currentFileMd5` | 全局变量 | 各自模块私有 |
| `showSection` | 全局函数 | `FileManager.showSection` |
| `startPolling` | 全局函数 | `ProcessingModule.startPolling` |
| 事件绑定 | HTML `onclick=` 属性 | `addEventListener` 在 `bindEvents()` 中 |
| `configureRules` | 全局函数（未通过 DomUtils 被调用） | 模块函数（通过 DomUtils 被调用） |

**根本问题**：HTML 模板仍在用 `onclick` 调用全局函数（遗留风格），但按钮回调和事件流已经迁移到模块系统。任何一方假设的变量状态在另一方可能不存在。

### 7.2 建议的长期解决方案

1. **消除全局函数**：将所有 `onclick="fn()"` 替换为 `addEventListener` 绑定
2. **统一状态管理**：用一个全局状态对象 `AppState = { currentFileMd5: null }` 替代分散的模块私有变量
3. **逐步淘汰 main.js**：将 main.js 中仍在使用全局 `currentFileMd5` 的函数（`deleteFile`, `resumeFile`, `updateProgress` 等）逐步迁移到模块中
4. **当前 hotfix 的局限性**：`window.currentFileMd5` fallback 是权宜之计，双轨并行一天，就有新入口路径出问题的风险

---

## 八、关键发现

1. **双轨架构是根源**：`main.js` 与 `modules/*.js` 各自管理状态，没有统一的同步机制
2. **防御性编程的必要性**：`window.currentFileMd5` fallback 能防止类似问题，但治标不治本
3. **HTML onclick 是遗留入口**：所有 `onclick="fn()"` 都应改为 `addEventListener` + 模块函数调用
4. **每个模块各自持有 currentFileMd5**：FileManager、ProcessingModule、RulesConfigModule 各有自己的副本，需要手动同步
