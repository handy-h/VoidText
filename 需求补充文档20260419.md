# 小说文本清洗工具 - 需求规格说明书

## 1. 项目概述

### 1.1 项目名称

小说文本智能清洗工具（Novel Text Cleaner）

### 1.2 项目目标

开发一个个人使用的桌面工具，用于清洗小说TXT文档中的错别字、乱码、广告、重复或缺失片段等问题。工具需要支持**文件生命周期追踪、处理进度恢复、多版本管理、自定义规则**等核心能力。

### 1.3 使用场景

- 单人使用，无需考虑多用户协作。
- 文件存储于本地，数据库使用 SQLite。
- 支持离线工作，所有处理均在本地完成。

### 1.4 技术约束

- 编程语言：Go
- 数据库：SQLite
- 文件标识：MD5
- 向量模型：本地或API（用户自行选择）
- 文本生成模型：支持本地或API（如DeepSeek-V3.2、qwen-max等）

## 2. 核心功能需求

### 2.1 文件上传与识别

| ID  | 需求描述                                                                                                                                                                              |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------- |
| F1  | 用户上传一个TXT文件，工具自动解析文件名，提取**作者**和**小说名称**。文件名格式固定为：`作者{{分隔符}}标题.txt`，分隔符支持用户自定义列表（在`.env`配置文件中配置，如`[" - ", "\_", " | "]`）。 |
| F2  | 计算文件的MD5值，作为该文件的唯一标识。                                                                                                                                               |
| F3  | 查询数据库：若MD5已存在，则根据该文件的生命周期状态决定行为（见2.4）；若不存在，则作为新文件创建处理记录。                                                                            |

### 2.2 处理生命周期

一个文件的生命周期包含以下状态：

- `pending`：已上传，等待开始处理
- `processing`：处理中（包含多个子步骤）
- `completed`：所有审核项已完成，生成了最终文件
- `failed`：处理失败（可重试）

子步骤（处理阶段）：

1. **基础清洗**：去除乱码、广告、特殊字符、繁体转简体等（使用本地 NLP 库 + duidui）。
2. **向量索引与检测**：分块向量化，检测重复段落、缺失片段。
3. **LLM修复**：调用文本生成模型修正错别字、语法错误。
4. **人工审核**：生成待审核列表，用户逐条确认或修改。
5. **生成最终文件**：所有审核通过后，输出清洗后的TXT。

> **注意**：步骤4（人工审核）是本工具的核心交互点，用户可能分多次完成审核。

### 2.3 处理进度与恢复

| ID  | 需求描述                                                                                                                                                                                                                                                                      |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| F4  | 工具提供**待处理列表**界面，展示所有状态不为`completed`的文件（按上传时间排序）。列表中显示：小说名称、作者、当前状态、最后更新时间。                                                                                                                                         |
| F5  | 用户可通过两种方式恢复处理进度：<br> a) **直接上传文件**：上传同一文件（MD5匹配）后，工具自动检测到未完成的处理记录，询问“是否继续上次进度”，确认后跳转到上次中断的步骤。<br> b) **从列表选择**：用户在待处理列表中选择一个文件，点击“继续处理”，直接进入该文件的处理工作流。 |
| F6  | 进度统计：按“待审核条目”的数量来展示百分比。例如，人工审核阶段共有100处待确认修改，用户已确认30处，则显示进度30%。                                                                                                                                                            |

### 2.4 版本链管理（核心特性）

| ID  | 需求描述                                                                                                                                                                                                                                                                                   |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| F7  | 用户在**任何处理阶段**都可以点击“下载当前处理后的文件”。下载的文件为中间版本，其MD5与原文件不同。                                                                                                                                                                                          |
| F8  | 当用户上传一个**中间版本文件**（之前从本工具下载的）时，工具应能识别出它属于哪一个原始文件，并**继续该原始文件的处理进度**（即从该中间版本对应的处理阶段往后走）。<br>例如：原始文件完成了“基础清洗”，用户下载了清洗后的文件。第二天上传该清洗后文件，工具应自动进入“向量索引与检测”阶段。 |
| F9  | 工具必须维护**版本链**：记录原始文件MD5与每个中间版本MD5的父子关系，确保任何版本都能追溯到原始文件。                                                                                                                                                                                       |

### 2.5 自定义规则

| ID  | 需求描述                                                                                                                                                                                                                                              |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| F10 | 用户可以对**每个文件单独设置处理规则**，包括但不限于：<br> - 自定义错别字映射表（如“高兴及了”→“高兴极了”）<br> - 广告关键词黑名单（正则表达式）<br> - 去重相似度阈值（0.0~1.0）<br> - 是否启用繁体转简体<br> - 是否启用LLM修复（可关闭以节省API费用） |
| F11 | 规则设置界面应在文件开始处理前展示，并允许在处理过程中修改（修改后后续步骤应用新规则）。                                                                                                                                                              |
| F12 | 规则配置随文件记录保存。当用户重新上传该文件（或其中间版本）并继续处理时，自动沿用上次的规则配置，用户也可选择覆盖规则。                                                                                                                              |

### 2.6 人工审核与修改追踪

| ID  | 需求描述                                                                                                                      |
| --- | ----------------------------------------------------------------------------------------------------------------------------- |
| F13 | 系统自动生成“待审核修改项”列表，每一项包含：原文片段、建议修改后文本、修改类型（错别字/乱码/广告/重复等）、置信度（来自AI）。 |
| F14 | 用户对每项可执行操作：**接受**、**拒绝**、**手动编辑**（修改建议文本）。                                                      |
| F15 | 所有审核操作记录到数据库，并作为最终文件生成的依据。                                                                          |
| F16 | 用户可随时中断审核工作，关闭工具。下次恢复时，待审核列表保持上次未完成的状态。                                                |

### 2.7 最终文件输出

| ID  | 需求描述                                                                                                                      |
| --- | ----------------------------------------------------------------------------------------------------------------------------- |
| F17 | 当所有审核项处理完毕（所有条目状态均为“已接受”或“已拒绝”），用户点击“生成最终文件”，工具根据审核结果输出清洗后的完整TXT文件。 |
| F18 | 最终文件命名规则：`{作者}_{小说名称}_cleaned_{时间戳}.txt`，并保存到用户指定的输出目录。                                      |
| F19 | 生成最终文件后，文件状态变更为`completed`，同时记录最终文件的MD5，纳入版本链。                                                |

### 2.8 其他功能

| ID  | 需求描述                                                                                                       |
| --- | -------------------------------------------------------------------------------------------------------------- |
| F20 | 工具提供“处理报告”导出功能（JSON或HTML），包含：文件基本信息、各步骤耗时、修改统计（按类型）、自定义规则快照。 |
| F21 | 支持删除文件记录（同时删除关联的中间文件？由用户选择是否保留文件）。                                           |

## 3. 数据模型设计（SQLite）

### 3.1 表结构

#### 表1：`files` - 文件主表

| 字段名         | 类型                 | 说明                                                                |
| -------------- | -------------------- | ------------------------------------------------------------------- |
| `id`           | INTEGER PRIMARY KEY  | 自增主键                                                            |
| `md5`          | TEXT UNIQUE NOT NULL | 文件的MD5值（当前版本）                                             |
| `original_md5` | TEXT                 | 原始上传文件的MD5（用于版本链）                                     |
| `author`       | TEXT                 | 作者（从文件名解析）                                                |
| `title`        | TEXT                 | 小说名称                                                            |
| `file_name`    | TEXT                 | 原始文件名                                                          |
| `file_size`    | INTEGER              | 文件大小（字节）                                                    |
| `status`       | TEXT                 | pending / processing / completed / failed                           |
| `current_step` | TEXT                 | 当前所处阶段（cleaning / indexing / llm_fix / review / finalizing） |
| `progress`     | INTEGER              | 进度百分比（0-100）                                                 |
| `rules_config` | TEXT                 | JSON格式，存储该文件的自定义规则                                    |
| `created_at`   | TIMESTAMP            | 首次上传时间                                                        |
| `updated_at`   | TIMESTAMP            | 最后更新时间                                                        |
| `error_msg`    | TEXT                 | 错误信息（若失败）                                                  |

#### 表2：`versions` - 版本链

| 字段名         | 类型                 | 说明                            |
| -------------- | -------------------- | ------------------------------- |
| `id`           | INTEGER PRIMARY KEY  |
| `original_md5` | TEXT NOT NULL        | 原始文件MD5                     |
| `version_md5`  | TEXT UNIQUE NOT NULL | 当前版本MD5                     |
| `parent_md5`   | TEXT                 | 上一个版本的MD5（根版本为NULL） |
| `version_type` | TEXT                 | original / intermediate / final |
| `file_path`    | TEXT                 | 该版本文件存储的绝对路径        |
| `created_at`   | TIMESTAMP            | 生成时间                        |

#### 表3：`review_items` - 人工审核项

| 字段名              | 类型                | 说明                                    |
| ------------------- | ------------------- | --------------------------------------- |
| `id`                | INTEGER PRIMARY KEY |
| `file_md5`          | TEXT NOT NULL       | 关联的文件MD5（当前处理版本）           |
| `original_text`     | TEXT                | 原文片段                                |
| `suggested_text`    | TEXT                | 建议修改后文本                          |
| `modification_type` | TEXT                | 错别字/乱码/广告/重复/缺失              |
| `confidence`        | REAL                | AI置信度（0-1）                         |
| `position_start`    | INTEGER             | 在文档中的起始字符位置                  |
| `position_end`      | INTEGER             | 结束位置                                |
| `status`            | TEXT                | pending / accepted / rejected / edited  |
| `edited_text`       | TEXT                | 用户手动编辑后的文本（若status=edited） |
| `created_at`        | TIMESTAMP           | 生成时间                                |
| `resolved_at`       | TIMESTAMP           | 处理时间                                |

#### 表4：`processing_logs` - 处理日志（可选，用于调试）

| 字段名      | 类型                | 说明             |
| ----------- | ------------------- | ---------------- |
| `id`        | INTEGER PRIMARY KEY |
| `file_md5`  | TEXT                | 关联的文件MD5    |
| `step`      | TEXT                | 步骤名称         |
| `action`    | TEXT                | 具体操作         |
| `details`   | TEXT                | JSON详情         |
| `status`    | TEXT                | success / failed |
| `timestamp` | TIMESTAMP           | 日志时间         |

### 3.2 索引建议

- `files(md5)` UNIQUE
- `files(original_md5)`
- `files(status)`
- `versions(version_md5)` UNIQUE
- `review_items(file_md5, status)`

## 4. 工作流程（文字描述）

### 4.1 首次上传并处理

1. 用户上传TXT文件。
2. 工具解析文件名，提取作者和小说名称（根据`.env`中配置的分隔符列表依次尝试）。
3. 计算文件MD5，查询数据库。
4. 若为新文件，创建记录，状态为`pending`。
5. 展示规则配置界面，用户确认或修改规则。
6. 开始处理：
   - 基础清洗（本地NLP + duidui）
   - 向量索引与重复/缺失检测
   - LLM修复（调用用户配置的模型API）
   - 生成待审核列表
7. 用户逐条审核修改项（接受/拒绝/编辑）。
8. 所有审核项完成后，生成最终文件，状态变为`completed`。
9. 若用户中途退出，保存当前进度（状态`processing`及当前步骤）。

### 4.2 恢复处理（方式一：直接上传）

1. 用户上传文件。
2. 计算MD5，查询数据库。
3. 若MD5存在且状态不为`completed`，提示“发现未完成任务，是否继续？”
4. 用户确认后，加载该文件的处理上下文，跳转到上次中断的步骤。

### 4.3 恢复处理（方式二：从待处理列表选择）

1. 打开工具，主界面显示待处理列表（所有`status != 'completed'`的文件）。
2. 用户选择一个文件，点击“继续处理”。
3. 加载该文件的处理上下文，跳转到上次中断的步骤。

### 4.4 版本链场景示例

1. 原始文件 `novel.txt` (MD5=A)。
2. 完成基础清洗后，用户下载中间文件 `novel_cleaned.txt` (MD5=B)。
3. 用户上传 `novel_cleaned.txt` → 系统查询 `versions` 表，找到 `original_md5=A`，`version_md5=B`，`parent_md5=NULL` → 确定这是原始文件的第一个中间版本。
4. 系统加载原始文件A的处理记录，但**文本内容使用B**，并从中断的步骤（向量检测）继续。

## 5. 非功能性需求

| 需求         | 说明                                                                           |
| ------------ | ------------------------------------------------------------------------------ |
| **可靠性**   | 任何步骤失败应能捕获错误，状态标记为`failed`，并提供重试按钮，不丢失已有进度。 |
| **可维护性** | 代码模块化：清洗模块、向量模块、LLM模块、审核UI模块、数据库模块相互独立。      |
| **易用性**   | 提供简单的图形界面。由于是个人使用，界面可简陋但功能完整。                     |
| **数据安全** | 所有文件处理和数据库操作均在本地，不上传任何内容（除非用户选择API模型）。      |

## 6. 技术选型（已确认）

| 组件             | 选型方案                                                                                                                                               |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------- |
| **基础文本清洗** | 本地 NLP 库 + duidui                                                                                                                                   |
| **向量模型**     | 用户自定义，支持本地或API。在 `.env` 文件中配置调用地址和模型名称（如 `VECTOR_MODEL_URL=http://localhost:8000/embed`, `VECTOR_MODEL_NAME=gte-base`）。 |
| **文本生成模型** | 用户自定义，支持本地或API。在 `.env` 文件中配置调用地址和模型名称（如 `LLM_API_URL=https://api.deepseek.com/v1`, `LLM_MODEL_NAME=deepseek-v3.2`）。    |
| **配置管理**     | 使用 `.env` 文件存储所有可配置项，包括：<br> - 文件名分隔符列表（如 `NAME*SEPARATORS=[" - ", "*", "                                                    | "]`）<br> - 向量模型和 LLM 的 API 地址、密钥、模型名称<br> - 本地文件存储路径、数据库路径等。 |
| **数据库**       | SQLite                                                                                                                                                 |
| **文件标识**     | MD5                                                                                                                                                    |

## 7. 验收标准

1. 能够正确解析文件名中的作者和小说名称（支持用户自定义的多种分隔符）。
2. 上传相同MD5文件能自动识别并恢复进度。
3. 上传中间版本文件能正确关联原始文件并恢复进度。
4. 待处理列表正确显示未完成文件。
5. 人工审核界面支持逐项确认、拒绝、编辑。
6. 自定义规则（如错别字映射）能应用到后续处理。
7. 最终文件生成后，再次上传该文件能识别为已完成，并允许重新应用新规则。
8. 所有操作（修改、审核）均记录在数据库中，可导出报告。
9. 用户可通过修改 `.env` 文件自由切换向量模型和文本生成模型（包括本地 Ollama 或各类 API）。

## 8. 附录：配置示例（.env）

```ini
# 文件名分隔符列表（JSON格式）
NAME_SEPARATORS=[" - ", "_", "|"]

# 向量模型配置
VECTOR_MODEL_URL=http://localhost:8000/embed
VECTOR_MODEL_NAME=damo/nlp_gte_sentence-embedding_chinese-base
VECTOR_MODEL_API_KEY=optional

# 文本生成模型配置
LLM_API_URL=https://api.deepseek.com/v1
LLM_MODEL_NAME=deepseek-v3.2
LLM_API_KEY=sk-xxxxxx

# 本地存储路径
DATA_DIR=./data
DATABASE_PATH=./data/novel_cleaner.db
```
