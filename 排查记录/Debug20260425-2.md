## 问题概述
VoidText 项目在处理文件时，本地模型（Ollama）未被使用，导致处理卡在 `llm_fix` 步骤，进度停留在 40%。

## 已完成的修复

### 1. 分块逻辑修复
**问题**：文件 `6f32ed28546fb02ec39873abace37cce` 只有 1 行，包含 417,701 个字符，没有换行符。原 `SplitIntoChunks` 函数按换行符分割，导致整个文件被当作一个 chunk。

**修复**：修改 `internal/processor/model_repairer.go` 中的 `SplitIntoChunks` 函数，处理超长段落：
- 当段落长度超过 `maxChars`（1500字符）时，按字符数分割
- 使用 rune 切片确保正确处理中文字符
- 将 1 个 chunk 分割为 279 个 chunk

### 2. 健康检查初始化修复
**问题**：健康检查管理器 `HealthCheckManager` 的 `runHealthChecks()` 函数使用 ticker，首次检查在 30 秒后才执行。在此期间，`ShouldUseLocalModel()` 返回 false（因为初始 `Healthy` 状态为 false），导致本地模型不被使用。

**修复**：修改 `internal/processor/health_check.go`，在 ticker 循环前立即执行一次健康检查：
```go
func (hcm *HealthCheckManager) runHealthChecks() {
    // 立即执行一次健康检查，避免初始状态为不健康
    hcm.performHealthChecks()
    
    ticker := time.NewTicker(hcm.checkInterval)
    defer ticker.Stop()
    
    for {
        select {
        case <-ticker.C:
            hcm.performHealthChecks()
        case <-hcm.stopChan:
            return
        }
    }
}
```

### 3. 状态管理器恢复修复
**问题**：恢复处理时，状态管理器保留旧的 `TotalChunks: 1`，与实际 chunk 数量（279）不匹配。

**修复**：修改 `internal/processor/model_repairer.go` 中的 `ProcessChunks` 函数，即使恢复处理也调用 `StartProcessing`：
```go
// 初始化状态管理器（恢复时也重新初始化，因为chunk数量可能变化）
if wp.stateManager != nil {
    wp.stateManager.StartProcessing(fileMd5, totalTasks, "llm_fix")
}
```

### 4. 配置调整
- **超时时间**：从 30 秒增加到 60 秒（`.env` 中的 `LOCAL_MODEL_TIMEOUT`）
- **Worker 数量**：从 10 减少到 1，避免 Ollama 并发处理导致超时
